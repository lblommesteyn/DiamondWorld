# DiamondWorldJAX Technical Specification

## 1. Purpose

DiamondWorldJAX is an importable Python package for pitch-level generative baseball simulation using JAX, NumPyro, and Flax Linen.

The project is a sibling to the existing DiamondWorld repository. DiamondWorld should be used as reference material for data provenance, simulation lessons, validation ideas, and baseline comparisons, but DiamondWorldJAX is not required to preserve DiamondWorld's current schema, PyTorch model structure, or simulator interfaces.

The primary goal is to build a calibrated, one-pitch-at-a-time generative simulator that can recover baseball game dynamics at both the pitch/play level and the inning/game level.

Initial delivery target:

- A Python module, not a service.
- Runnable scripts/notebooks may import the package directly.
- A future external API and counterfactual decision interface should be possible, but are not part of V0.

## 2. Core Requirements

V0 must support:

- Pitch-level sequence modeling, one pitch per timestep.
- Full transition-state generation after each pitch/play.
- Joint NumPyro/Flax training with SVI and an AutoLowRank guide.
- Flax Linen deterministic modules inside the probabilistic model.
- Player-season latent embeddings generated by a stats encoder.
- League-level priors for MLB and MiLB, with MLB required first and MiLB preferred when data access is practical.
- Rule-era indicators for shift restriction and pitch clock.
- Stochastic fatigue/latent drift.
- Manager decision modeling from the beginning, even if the first model is simple.
- Teacher-forced next-pitch/play calibration.
- Non-teacher-forced full-game posterior predictive replay.
- Single-game calibration as the first success demo.
- Explicit internal decision boundaries for future counterfactual interventions.

V0 should use 2015+ Statcast-rich data and restrict training to rows/seasons with sufficient tracking quality for pitch and batted-ball modeling.

## 3. Non-Goals For V0

The following are out of scope for V0:

- Public web/API service.
- Stable external counterfactual API.
- Weather integration.
- Catcher/framing model.
- Explicit rest-day modeling.
- Detailed travel/schedule fatigue modeling.
- Full aerodynamic projectile simulation.
- Full defensive alignment reconstruction beyond rule-era and learned/latent approximations.
- Perfect MiLB ingestion if data availability becomes a blocker.
- Research-paper-quality exposition.

## 4. Architecture Summary

The model advances one pitch at a time:

```text
state_t
  -> manager_decision_t
  -> pitch_decision_t
  -> pitch_package_t
  -> pitch_execution_t
  -> swing/take tree
  -> contact/foul/in-play tree
  -> batted_ball_physics_t
  -> fielding/running/side_event transition_t
  -> state_{t+1}
```

Each pitch step should emit both intermediate generated variables and the final post-pitch/post-play transition state.

The implementation should keep these boundaries explicit. Later counterfactual code should be able to override decision objects and then reuse the same downstream execution, physics, and transition modules.

## 5. Package Boundaries

DiamondWorldJAX should initially be an importable Python package with internal modules for:

- Data ingestion and schema building.
- Sequence batching and masking.
- Game state representation.
- State transition utilities.
- Player-season stat encoders.
- Bayesian priors and NumPyro model entry points.
- Flax Linen deterministic modules.
- Training loops.
- Posterior predictive simulation.
- Calibration reports.

No formal file/module layout is required by this spec, but the code should avoid monolithic scripts. Model components should be separable enough to test in isolation and compose in the joint model.

## 6. Data Scope

### 6.1 Training Era

Use 2015+ data as the initial modeling era.

Training should be restricted to data with enough tracking quality to support:

- Pitch package generation.
- Pitch location/execution modeling.
- Swing/take and contact-path modeling.
- Batted-ball physics modeling.
- Full state transition reconstruction.

### 6.2 League Scope

Initial prior design should support:

- MLB.
- MiLB.

MLB ingestion can be the first runnable target. MiLB support should be represented in schema and priors, but does not need to block the first single-game calibration demo.

### 6.3 DiamondWorld Relationship

DiamondWorld may be used to inspect:

- Current Statcast fetching/caching.
- Current pitch-level schema.
- Current validation logic.
- Current baselines.
- Current evaluation metrics.
- Lessons from pitch-level and game-context simulation.

DiamondWorldJAX should not be constrained to DiamondWorld's current processed schema.

## 7. Expanded Schema

The primary training unit is a pitch row. Game-level sequences are formed by sorting pitch rows within each game.

The schema should use nullable columns and explicit masks. Missing conditional targets should be represented by masks, not by overloaded sentinel values when avoidable.

### 7.1 Identity Fields

Required or preferred identity fields:

```text
game_id
season
league_id
game_date
park_id
home_team_id
away_team_id
batting_team_id
fielding_team_id
pitcher_id
batter_id
pitcher_season_id
batter_season_id
pitcher_hand
batter_side
lineup_slot
```

Player-season IDs should be stable keys used by the embedding encoder and player stat table.

### 7.2 Pre-Pitch State

Pre-pitch game state:

```text
inning
half_inning
balls
strikes
outs
base_state
runner_on_1b_id
runner_on_2b_id
runner_on_3b_id
home_score
away_score
score_diff_batting
pitch_count_game
pitch_count_inning
pitch_count_plate_appearance
times_through_order
plate_appearance_index
pitch_index_game
pitch_index_plate_appearance
```

`base_state` may remain a bitmask, but runner IDs are needed for steals, baserunning, and player-derived transition effects.

### 7.3 Rule-Era Fields

V0 rule indicators:

```text
shift_restricted
pitch_clock
```

These should be deterministic from date/season when possible, but stored or materialized as model inputs.

### 7.4 Manager/Decision Fields

Observed or inferred manager/strategic decisions:

```text
pitching_change
new_pitcher_id
steal_attempt
runner_send_decision
defensive_alignment_proxy
pinch_hitter_used
pinch_runner_used
```

V0 may use simple inferred labels and masks. The important requirement is that manager decisions are represented as distinct model variables rather than fused into outcomes.

### 7.5 Pitch Package Fields

Observed pitch package and execution fields:

```text
pitch_type
target_x
target_z
plate_x
plate_z
zone_x_norm
zone_z_norm
release_speed
pfx_x
pfx_z
release_pos_x
release_pos_y
release_pos_z
release_extension
spin_rate
spin_axis
```

Target location is not directly observed in standard public data. V0 may infer latent `target_x` and `target_z` while training actual `plate_x` and `plate_z`.

Location should be height-normalized for batter-specific zone geometry. Raw plate coordinates should also be retained.

### 7.6 Hurdle Path Fields

Pitch-level decision/outcome path:

```text
swing
take
called_strike
called_ball
contact
whiff
foul
foul_tip
foul_bunt
in_play
plate_appearance_terminal
```

The hurdle tree should be represented by conditional masks. For example, `contact` is only observed/valid when `swing == true`.

### 7.7 Batted-Ball Fields

Batted-ball physics fields:

```text
launch_speed
launch_angle
spray_angle
hc_x
hc_y
bb_type
hit_distance
landing_x
landing_y
hang_time
```

Not every source will provide every field. V0 should prioritize the fields available in 2015+ Statcast and mask the rest.

Spray angle may be derived from `hc_x`/`hc_y` if direct spray angle is unavailable.

### 7.8 Transition Fields

Full transition-state fields:

```text
event_type
outs_added
runs_scored
base_state_after
runner_on_1b_after_id
runner_on_2b_after_id
runner_on_3b_after_id
balls_after
strikes_after
outs_after
inning_after
half_inning_after
home_score_after
away_score_after
plate_appearance_terminal_after
error_flag
steal_flag
caught_stealing_flag
wild_pitch_flag
passed_ball_flag
balk_flag
```

The transition model must support events that are not ordinary batted-ball outcomes, including steals, errors, wild pitches, passed balls, and balks.

## 8. Tensor Conventions

Primary training unit: one padded game sequence.

Recommended axis names:

```text
B = batch size, in games
T = max padded pitch steps per game
H = pitch history window length
S = state feature dimension
A = pitch/action/package feature dimension
M = manager decision feature dimension
Y = transition/output feature dimension
P = player-season count
D = latent embedding dimension
K = number of categorical classes for a head
```

### 8.1 Batch Tensors

Core tensors:

```text
game_state_pre        float/int  (B, T, S_pre)
game_state_post       float/int  (B, T, S_post)
manager_obs          mixed      (B, T, M)
pitch_package_obs    mixed      (B, T, A)
hurdle_obs           bool/int   (B, T, H_obs)
batted_ball_obs      float/int  (B, T, BIP)
transition_obs       mixed      (B, T, Y)
player_ids           int        dict[str, (B, T)]
team_ids             int        dict[str, (B, T)]
rule_features        float/int  (B, T, R)
history_indices      int        (B, T, H)
```

The exact representation may be split into dictionaries by target type. Categorical and continuous targets should not be forced into one homogeneous array if that makes masking or likelihood code brittle.

### 8.2 Masks

Required masks:

```text
pitch_valid_mask              bool  (B, T)
history_valid_mask            bool  (B, T, H)
manager_decision_mask         bool  (B, T, M)
pitch_package_mask            bool  (B, T, A)
swing_mask                    bool  (B, T)
take_mask                     bool  (B, T)
called_strike_ball_mask       bool  (B, T)
contact_mask                  bool  (B, T)
foul_mask                     bool  (B, T)
in_play_mask                  bool  (B, T)
batted_ball_mask              bool  (B, T, BIP)
transition_mask               bool  (B, T, Y)
terminal_pitch_mask           bool  (B, T)
```

Mask semantics:

- `pitch_valid_mask == false` means padded pitch row.
- Conditional likelihoods must only contribute where their condition and target mask are true.
- Non-terminal pitches should not contribute to terminal event likelihoods except through count/state updates.
- Batted-ball physics targets should only contribute when `in_play == true` or when the relevant contact/foul physics branch is active.

### 8.3 Player Stat Tensors

Player-season stat inputs:

```text
player_stats          float  (P, F_player)
player_league_id      int    (P,)
player_hand_features  int    (P, F_hand)
player_valid_mask     bool   (P,)
```

The exact stat list should remain configurable. V0 should support changing the stat vector without rewriting the embedding machinery.

### 8.4 Posterior Predictive Outputs

Posterior predictive generation should support:

```text
draws                 D_s
generated_game_state  (D_s, B, T, S_post)
generated_pitch_pkg   dict of arrays with leading (D_s, B, T)
generated_hurdles     dict of arrays with leading (D_s, B, T)
generated_batted_ball dict of arrays with leading (D_s, B, T)
generated_transition  dict of arrays with leading (D_s, B, T)
```

For non-teacher-forced replay, later generated states must depend on earlier generated states, not observed states.

## 9. Model Components

### 9.1 Player-Season Embedding Encoder

The embedding encoder maps configurable player-season stat vectors to latent embeddings.

Inputs:

```text
player_stats
league_id
handedness features
role indicators when available
```

Outputs:

```text
player_z              (P, D)
pitcher_z lookup      (B, T, D)
batter_z lookup       (B, T, D)
runner_z lookups      (B, T, bases, D)
fielder/team_z        (B, T, D_team)
```

Requirements:

- League-level priors for MLB and MiLB.
- Player-season granularity.
- Latent vectors, not hand-labeled skill axes, in V0.
- Handedness matchup effects should be hierarchical and computed from pitcher/batter handedness plus embeddings.

### 9.2 Fatigue / Latent Drift

Fatigue is a stochastic latent drift process that evolves within game.

Inputs:

```text
pitcher_z
batter_z
current game state
pitch count
recent pitch package
recent pitch outcomes
rule features
```

Outputs:

```text
fatigue_state_t
fatigue_state_{t+1}
```

Fatigue must be able to affect:

- Pitch selection.
- Stuff/velocity/movement.
- Command/location error.
- Batter swing/contact response.

V0 does not need rest-day modeling. Fatigue can reset or initialize at game/appearance boundaries.

### 9.3 Manager Decision Model

Manager decisions are part of V0.

Initial decisions:

```text
pitching_change
steal_attempt / hold
runner_send / hold when observable or inferable
defensive_alignment_proxy
pinch decision placeholders
```

The first implementation may be simple, but manager decisions must be separate variables so they can later be overridden in counterfactual rollouts.

Inputs:

```text
game state
lineup/pitcher usage
player embeddings
fatigue state
score/inning/context
rule-era indicators
```

Outputs:

```text
manager_decision_t
manager_decision_logits/parameters
```

### 9.4 Pitch Package Transformer

Use a deterministic Flax Linen sequence module over the last `H` pitches.

Inputs:

```text
history of pitch packages
history of hurdle outcomes
history of transition states
current game state
pitcher_z
batter_z
matchup_z
fatigue_state_t
manager_decision_t
rule features
```

Outputs should jointly define a pitch package:

```text
pitch_type distribution
latent pitch intent
target_x, target_z distribution
release_speed distribution
pfx_x, pfx_z distribution
release geometry distribution
spin distribution where available
```

The transformer should be trained with teacher forcing for one-step prediction and evaluated with multi-step/free rollout.

The pitch package generator should generate the whole package, not only pitch type.

The pitch package transformer is the first shared sequence-context module. It should
produce a contextual representation that can be reused by downstream heads when
appropriate. In particular, the swing/take model may consume the same history-aware
context representation rather than using an isolated non-sequential MLP.

### 9.5 Command / Execution Model

The execution model converts intended pitch location into actual pitch location.

Conceptual form:

```text
actual_location = target_location
                + pitcher command error
                + pitch-type miss pattern
                + fatigue drift
                + residual noise
```

Inputs:

```text
target_x, target_z
pitch_type
pitcher_z
batter_z
matchup_z
fatigue_state_t
count/game state
```

Outputs:

```text
plate_x
plate_z
zone_x_norm
zone_z_norm
command_error
```

### 9.6 Swing / Take Hurdle

The primary hurdle tree starts with swing/take:

```text
swing?
  no:
    called_strike vs ball
  yes:
    contact?
      no:
        whiff
      yes:
        foul vs in_play
```

Called strike/ball should support an optional umpire-error distribution that can be toggled on/off. V0 does not need umpire identity modeling, but the interface should permit an error/noise layer around the geometric strike zone.

Inputs:

```text
shared transformer context
actual pitch package
target/intent if available
game state
pitcher_z
batter_z
matchup_z
fatigue_state_t
rule-era indicators
```

Outputs:

```text
swing probability/logit
called_strike probability/logit
contact probability/logit
foul probability/logit
in_play probability/logit
```

The swing decision should be modeled as a transformer-backed logit head:

```text
swing_logit_t = SwingHead(
    shared_context_t,
    executed_pitch_t,
    batter_z,
    pitcher_z,
    matchup_z,
    fatigue_state_t,
    game_state_t,
)
```

Swing behavior must be explicitly conditional on the batter embedding. This is
analogous to pitch package generation being explicitly conditional on the pitcher
embedding. The batter embedding should control swing tendencies such as zone
discipline, chase behavior, aggression by count, contact selectivity, and matchup
response. Pitcher and pitch-package information still matter, but batter-specific
latent behavior should be a first-class input to the swing head.

The no-swing path then uses a called-strike/ball head. The swing path uses
contact, foul, and in-play heads. These downstream heads may also reuse
`shared_context_t`, but must preserve the conditional hurdle masks.

### 9.7 Batted-Ball Physics

For contact branches, generate batted-ball physics.

Initial generated fields:

```text
launch_speed
launch_angle
spray_angle
landing_x
landing_y
hit_distance
```

Use the least computationally expensive approach that produces useful calibration. V0 may use learned analytic approximations rather than full projectile physics.

The park transform should encode park geometry and apply transformations to the batted-ball trajectory/landing/catchability. Park effects should not be treated merely as a flat hierarchy if geometry is available.

Inputs:

```text
pitch package
execution/location
batter_z
pitcher_z
matchup_z
fatigue_state_t
park geometry/features
rule-era indicators
```

Outputs:

```text
batted-ball continuous fields
park-adjusted landing/carry fields
catch/hit/error-relevant features
```

### 9.8 Fielding, Running, Side Events, And Transition Model

The transition model produces the full post-pitch state.

It should combine:

- Rule-consistent state engine logic.
- Learned probabilities from player/team embeddings.
- Physics outputs for batted balls.
- Side-event processes for steals, errors, wild pitches, passed balls, balks.

Team defense may initially be represented as a concatenation/aggregation of individual player embeddings.

Runner decisions and baserunning outcomes should derive from latent player embeddings and game state.

Outputs:

```text
event_type
outs_added
runs_scored
base_state_after
runner ids after
balls_after
strikes_after
outs_after
inning_after
half_inning_after
score_after
side event flags
```

The state engine should enforce valid baseball transitions during rollout where possible.

## 10. Training And Inference

### 10.1 Joint Objective

The model should be optimized jointly because:

- Player-season embeddings affect multiple downstream modules.
- Fatigue affects pitch selection, stuff, command, and batter response.
- Pitch package generation and outcome generation must co-adapt.
- Calibration across pitch and game dynamics depends on shared latent structure.

### 10.2 Inference Method

Use NumPyro SVI with AutoLowRank as the default guide family.

Staged warm starts are allowed and likely necessary, but the final V0 calibration path should support joint SVI.

### 10.3 Flax Modules In NumPyro

Deterministic neural components should use Flax Linen.

Flax modules may include:

- Player stat encoder.
- Pitch package transformer.
- Manager decision network.
- Physics residual maps.
- Transition heads.

Their parameters should be included in the joint optimization path. The code should make it clear which parameters are deterministic neural parameters and which are probabilistic sample sites.

### 10.4 Training Modes

Required training/evaluation modes:

```text
teacher_forced_one_step
free_replay
posterior_predictive
```

Teacher-forced one-step mode:

- Uses observed history and observed state.
- Scores the observed next pitch package, hurdle path, batted-ball fields, and transition.

Free replay mode:

- Starts from an observed initial game state.
- Generates subsequent states autoregressively.
- Does not use observed future states as inputs.

Posterior predictive mode:

- Draws from posterior/guide samples.
- Produces multiple generated game trajectories.
- Feeds calibration reports.

## 11. Calibration And Evaluation

The first success demo is single-game calibration.

### 11.1 Pitch-Level Metrics

Evaluate:

```text
pitch_type NLL / calibration
pitch package continuous likelihood or distribution checks
target/location calibration
release speed/movement distribution checks
swing calibration
called strike/ball calibration
contact calibration
foul/in-play calibration
batted-ball EV/LA/spray distribution checks
transition-state calibration
```

### 11.2 Inning/Game-Level Metrics

Evaluate posterior predictive rollouts against observed game dynamics:

```text
zero-run inning rate
inning run distribution
big-inning tail probability
run autocorrelation / clustering
full-game score distribution
team runs per game
plate appearance length distribution
pitch count distribution
```

### 11.3 Baselines

Compare against relevant DiamondWorld baselines at both pitch and inning levels:

- Existing DiamondWorld Phase 3/4 where applicable.
- MarkovRE24.
- Bayesian hurdle baseline.
- SVI-ARMA inning model.
- Empirical resampling baselines.

The exact baseline harness can be adapted from DiamondWorld but does not need to share schema internals.

## 12. Counterfactual Readiness

V0 does not expose a public counterfactual API, but model internals must preserve decision boundaries.

Future interventions should be able to override:

```text
manager_decision_t
pitch_decision_t
pitch_type
target_location
steal_attempt
runner_send_decision
defensive_alignment_proxy
pitching_change
```

Downstream modules must consume overridden decisions exactly as they consume generated or observed decisions.

The internal design should follow:

```text
state -> decision -> action/package -> execution/physics -> outcome -> next_state
```

Avoid fusing decisions directly into outcome heads when a distinct decision object can be represented.

## 13. Validation Expectations

Data validation should check:

- Required columns exist.
- Type consistency.
- Pitch sequence ordering within games.
- Pre/post state consistency.
- Count transitions.
- Inning/half-inning transitions.
- Base/out/runs validity.
- Mask consistency for conditional targets.
- Player-season ID lookup consistency.
- Rule-era feature consistency.

Model validation should check:

- Batch shapes.
- Masked likelihood behavior.
- JIT compatibility where intended.
- Posterior predictive output shapes.
- Non-teacher-forced rollout does not read future observed state.
- Generated transitions remain valid or are repaired by the state engine.

## 14. V0 Acceptance Target

V0 is considered minimally successful when it can:

1. Build an expanded 2015+ pitch-level dataset for at least MLB games.
2. Create padded JAX game-sequence batches with all required masks.
3. Fit a small joint NumPyro/Flax model with SVI AutoLowRank.
4. Run teacher-forced next-pitch/play calibration for one held-out game.
5. Run non-teacher-forced posterior predictive replay for that game.
6. Produce pitch-level and inning/game-level calibration summaries.
7. Keep decision/action/outcome boundaries explicit enough for later counterfactual hooks.
